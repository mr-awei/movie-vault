## 原始审查结论（修复前基线，存档）

### A 档（建议尽快处理）

### A-1 持久化双轨：data.json 仍在持续写盘
- 证据：`store.ts:444` `writeFileSync(dbPath, JSON.stringify(cache))` + `scheduleSave/flushSave` 仍活跃（`video.ts:458/475` 等 5 处调用点）；`store.ts:437` 同步兜底写。
- 问题：SQLite 已是主存储，但 data.json 仍随每次视频变更全量序列化写盘。风险：①双写不一致（启动 migrateInPlace 可能用旧 JSON 回灌）；②大库时每次写几百 KB JSON 的 IO 抖动；③磁盘体积双份。
- 建议：迁移完成后把 JSON 写路径收敛为「仅迁移期写 + 只读兼容」。最小改动：`flushSave` 在 SQLite 有数据时直接 return（保留首次迁移备份）。

### A-2 IPC 边界 `any` 入参无运行时校验
- 证据：`ipc/settings.ts:9` `patch: any`、`ipc/video.ts:30/34` `filter/patch: any`、`ipc/system.ts:244` `settings: any`。
- 问题：类型约束只存在于编译期；主进程对渲染进程传入的任意字段直接写库（`repo.updateVideo(id, patch)`）。单窗口本地应用风险有限，但任一 XSS/注入点即升级为任意写库。
- 建议：`videoUpdate` / `settingsSet` 加最小字段白名单校验（只允许已知键），`proxyTest` 收敛为显式参数。

## B 档（中等，按收益排序）

### B-1 弱密码哈希（隐私锁）
- 证据：`ipc/system.ts` `sha256(salt + password)` 单轮无迭代。
- 问题：GPU 可秒级爆破 6 位内 PIN；隐私锁形同虚设。
- 建议：改 `crypto.scryptSync(password, salt, 32)`（node 内置，无新依赖）；旧哈希检测长度 64 位 hex 时视为旧格式并引导重设。

- 建议（低优先级，P2-1 已评估过 ROI）：App.tsx 若再动，只抽「过滤链 + 批量操作编排」两个 hook；其余保持，避免为拆而拆引入回归。

### B-3 渲染层非空断言 39 处
