### 1.2 架构现状

```
渲染进程 (React)

  ├─ components/ (30+组件，SettingsModal 1628行 / VideoDetail 1101行 / Sidebar 872行)

       └─ SQLite (db.ts：yinghai.db，表结构已建，仅 watch_history 表实际使用)
```

### 1.3 核心技术债判断

1. **数据存储半迁移**：SQLite 表结构完整、migrate.ts 迁移脚本完整，但 repo.ts 完全不写 SQLite，双存储并存是最大的一致性风险源。
2. **状态管理半迁移**：Zustand 只接管了弹窗开关，业务状态（视频列表、11个筛选Set、播放列表、多选集、扫描进度）全部堆在 App.tsx，任何状态变化触发整树重渲染。
3. **组件未拆分**：App / SettingsModal / VideoDetail / Sidebar 四个超大型组件，props drilling 极值（Sidebar 接收 80+ props）。
4. **IPC 层未分层**：1897 行单文件，业务逻辑（封面验证、改名回写、多源合并）与协议层混在一起。

### 1.4 做得好的地方（不应在优化中破坏）

- `VirtualizedWall` 海报墙虚拟化设计正确（rAF 节流 + OVERSCAN 3）
- JSON 存储的防抖写盘 + 原子 rename + 外部修改检测机制成熟
- `Toast` 模块级单例，无 props drilling
- `posterUrlCache` 5000 条上限 + `?v=N` 版本号解决封面刷新
- ECharts 实例在 cleanup 中统一 dispose，无内存泄漏
- 隐私锁 SplashScreen 在设置加载前不渲染内容
- 单实例锁 + 升级杀旧进程方案考虑周到（虽然实现有重复调用 bug，见 P0-1）

### P0-1 单实例锁在同一进程内被调用两次，极端情况下启动即自杀

| 维度 | 内容 |
|---|---|
| **证据** | `src/main/index.ts:106-116` 第一次调用 `app.requestSingleInstanceLock()` 并注册 `second-instance`；`:347-361` 第二次调用同一函数，再次注册监听器，且第二次失败时执行 `process.exit(0)` |

| **方案** | 删除 106-116 行的提前退出分支，仅保留 347-361 的完整版（含 restore 逻辑） |
| **难度** | 极低（删 10 行） |
| **影响** | 启动稳定性 |

### P0-2 `lm://` 自定义协议无路径白名单，可读任意本地图片

| 维度 | 内容 |
|---|---|
| **证据** | `src/main/index.ts:187-206` `protocol.handle('lm', ...)` 中 base64 解码出任意绝对路径，仅校验扩展名后直接 `fs.readFile` 返回；`:128-130` 注册协议时设 `bypassCSP: true` |

## 四、P2 低优先级（长期技术债，规划性重构）

### P2-1 App.tsx 按业务域拆自定义 hook

将 2901 行的 App.tsx 拆为：`useLibraryData`（reconcile/allReconciles/libraries）、`usePlaylist`、`useSelection`、`useScanProgress`、`useRecommendQueue`。预计 App.tsx 降到 ~600 行壳组件。这是 P1-4（useFilterStore）的自然延伸。

### P2-2 `text-white/X` → `text-ink-*` 语义化主题变量

`index.css:89-109` 有 21 条 `.theme-light .text-white/* { color: ... !important }` 覆盖规则，根因是组件直接写 `text-white/70` 而非语义变量。长期逐步替换为 `text-ink-*`，删掉 `!important` 覆盖。新增 `text-white/33` 等透明度档位就要加一条 CSS 的脆弱模式将消除。

### P2-3 preload 层类型化

`preload/index.ts:47,72,79,102` 用 `payload as never` 绕过类型检查。在 `shared/api-types.ts` 为每个事件定义具体 payload 类型（`PosterFetchedPayload / ScanProgressPayload / PreviewTaskEventPayload`），主进程推送 payload 形状变化时渲染端有编译错误。

### P2-4 原生 dialog 替换为自建模态

`App.tsx:1177,1185,1210,1214,1223,1241,1328,1332` 多处 `window.alert` / `window.prompt`，Electron 中原生对话框样式与应用主题脱节且阻塞 UX。封装 `<PasswordPromptModal>` 替代 `window.prompt`，toast 替代 `window.alert`。

### P2-5 `previewTasks` / `previewManifests` 从 data.json 移出

预览任务队列和 manifest 是临时数据，不该进全量 JSON 序列化（`store.ts` DBShape）。`claimNextPreviewTask`（`repo.ts:291-310`）每次全表 filter+sort。单独存 `preview-queue.json` 或直接用 SQLite 表（db.ts 已有 infrastructure），内存维护 pending 队列（Array，入队 push 出队 shift）。

### P2-6 插件系统：借鉴 Stremio 无状态 HTTP Addon 协议

中期可考虑将刮削器、字幕源、弹幕源、AI 海报等做成插件。Stremio 的 Addon 是"无状态 HTTP 服务"，暴露 `/catalog`、`/meta`、`/stream`、`/search` 4 个 REST 端点（[Stremio Addon 协议](https://gist.github.com/dipandhali2021/96559332a40269f911e043d864f8763f)）。比 Jellyfin 式进程内 DLL 插件更安全（沙箱、崩溃不拖垮主进程）、跨语言（Python/Go/Node 都行）、调试方便（curl 直连），与 Electron 主进程天然契合。

### P2-7 内置 Backup / Restore 一键导出

设置页加"导出库"按钮：打包 SQLite db + NFO + 海报为 zip；导入时做 schema 版本检查。Jellyfin 10.11 已加入内置 Backup/Restore（[Jellyfin 备份](https://jellyfin.org/docs/general/administration/backup-and-restore/)）。用户换机器/重装系统不丢刮削结果。

### P2-8 其他零散项

- `proxy.ts:25-32` dispatcher 缓存覆盖前未 `close()` 旧实例，切换代理设置泄漏 socket
- `playlist.ts:75-85` `reorderPlaylist` 不去重，UI 传入重复 videoIds 时会重复
- `openlibrary.ts:185-210` 把书当电影抓（作者当导演、页数当片长），应从聚合链移除或加字段合理性校验
- `images.ts:68-103,373-428` `generateFrame` / `generatePreviewSet` 是死代码（已被 preview-v2 替代），删除
- `App.tsx:94-96` `RES_ORDER/DUR_ORDER/SCORE_ORDER` 硬编码中文标签同时作为 facet key，英文界面不翻译，应 key 用英文 token
- `VirtualizedWall.tsx:151` 行 key 用 `${e.code}-${ci}` 含列索引，排序后强制卸载重挂载，应只用 `e.video?.id`
- `index.ts:421-444` 自动更新检测 `setInterval` 每 30 分钟跑一次，未在 app quit 时 clearInterval（虽然进程退出会回收，但不规范）

## 七、总结

影海 v2.9.2 是一个功能完整、考虑周到的本地影视管理应用——JSON 存储的防抖/原子写/外部修改检测、海报墙虚拟化、隐私锁、单实例升级杀进程等设计都体现了对细节的打磨。当前最紧迫的问题不是"缺功能"，而是**三处"半迁移"状态积累的技术债**：

1. **数据存储半迁移**（JSON↔SQLite 双轨并存）—— P1-1，决定中长期性能上限
2. **状态管理半迁移**（Zustand 只接管弹窗）—— P1-4 + P2-1，决定渲染性能和可维护性
3. **组件/IPC 半拆分**（四个超大型文件）—— P1-8 + P1-12 + P1-13 + P2-1

建议按"P0 快速修复（1-2天）→ P1 核心重构（1-2周）→ P2 长期规划"的节奏推进。P0 的 10 项都是小改动，修完后用户可感知的稳定性和性能会有明显提升；P1 的数据存储决策是最关键的架构选择，建议尽早定方向。
